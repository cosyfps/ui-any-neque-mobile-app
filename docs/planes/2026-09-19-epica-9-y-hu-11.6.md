# Plan — HU-11.6 y Épica 9: rediseño de la App del Entrenador

## Contexto

La app del Alumno está terminada, auditada y corregida: 11 pantallas contra mocks, 761
tests, contraste AA medido sobre el DOM y las tres reglas globales verificadas. El PR #9
la lleva a `develop`.

El Entrenador, en cambio, **no existe**. Hoy `/trainer/dashboard`, `/trainer/clients`,
`/trainer/routines` y `/trainer/profile` cargan las cuatro el mismo `DashboardPage`, con
`state` fijo en `'success'`, el saludo con el nombre codificado a mano y las métricas en
guion. Un entrenador que pulse «Clientes» cree que la app está rota.

Esta etapa hace tres cosas: cierra los seis hallazgos que quedaban de la auditoría,
**rediseña el rol Entrenador de cero** —el esqueleto actual se descarta, no se extiende— y
alinea el contrato del front con el modelo de datos acordado para el BFF.

El modelo está en [`docs/modelo-datos.md`](../modelo-datos.md): 19 tablas y 19 decisiones
cerradas. Tres de esas decisiones cambian tipos que el front ya usa, así que entran aquí,
antes de conectar el BFF.

| Hallazgo                                                                                     | Consecuencia                                                                                                                    |
| -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `STUDENTS_PORT` solo tiene `getById`, `listByTrainer` y `update` de campos del propio alumno | Faltan `create` y `setStatus`. **El backlog afirma que la Épica 9 «extiende adapters en vez de rehacer puertos»: es falso.**    |

| `Routine` ya trae `trainerId` y `studentId`; `Assessment` está completo                      | La asignación y las evaluaciones no necesitan modelo nuevo.                                                                     |

| Descartar `trainer-layout` y `dashboard` borra sus specs                                     | La cobertura baja de golpe al empezar y se recupera al cerrar HU-9.3. No es regresión.                                          |
| `AppNotification.actionRoute` guarda `/student/routine` como dato                            | Acopla la base a las rutas del front. Pasa a `targetType` + `targetId`, y el mapeo a ruta vive en el front.                     |
| `WorkoutExerciseLog` solo cuenta series completadas                                          | No guarda con qué peso ni cuántas repeticiones. Sin eso el entrenador no puede ver progresión de carga: es **alcance nuevo**.   |
| `SCHEDULE_PORT.cancel(sessionId, reason)` recibe un motivo que nada persiste                 | La firma pasa a motivo predefinido más nota libre.                                                                              |

### HU-9.12 — Alineación del contrato con el modelo de datos

Rama: `refactor/NEQUE-9.12-contrato-modelo-datos`

Estas tres decisiones de [`docs/modelo-datos.md`](../modelo-datos.md) cambian tipos que el
front ya usa. Se hacen ahora, contra los mocks, para que conectar el BFF no obligue a
tocar `domain`, `application` ni `ui`.

| Ticket   | Qué hace                                                                                                                                       |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| T-9.12.1 | `AppNotification` cambia `actionRoute` por `targetType` + `targetId`, con el enum `NotificationTarget`. Toca modelo, adapter, semilla y spec.  |
| T-9.12.2 | Mapa `targetType` → ruta en `ui/shared`, con su spec. La página de notificaciones deja de navegar a una cadena que venía de datos.             |
| T-9.12.3 | `WorkoutSet` en `domain/workouts`, y `WORKOUTS_PORT.logSet` pasa a recibir peso y repeticiones reales de la serie. Adapter, semilla y specs.   |
| T-9.12.4 | El runner captura peso y repeticiones reales al cerrar cada serie, con lo prescrito como sugerencia. Es la única pantalla que cambia de flujo. |
| T-9.12.5 | `CancelReason` en `domain/schedule` y `SCHEDULE_PORT.cancel(sessionId, reason, note)`. Adapter, semilla y la página de agenda.                 |

**Por qué el runner cambia de flujo:** hoy «Serie completada» es un solo toque. Para
registrar carga real tiene que capturar dos números. El riesgo es volverlo pesado en medio
del entrenamiento, así que los campos llegan precargados con lo prescrito y confirmar sin
tocarlos debe costar el mismo toque que hoy.

## Riesgos y mitigaciones

| Riesgo                                                             | Mitigación                                                                                                                                                 |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Budget de 500 kB con 4.8 kB de margen**                          | Todo `/trainer` en su chunk lazy, igual que `/student`. El QR se importa dinámicamente dentro de su pantalla. `npm run build` en cada ticket de pantalla.  |
| **Cobertura del 80%** con ~40 archivos nuevos                      | Orden dominio → aplicación → UI: el código denso se cubre primero y las páginas quedan tontas. `AsyncState` ya centraliza las ramas de estado.             |
| Borrar el shell del entrenador tira su cobertura                   | Ocurre dentro de HU-9.3 y se recupera en el mismo PR con los specs del shell nuevo.                                                                        |
| `Exercise.ownerTrainerId` cambia un modelo en uso                  | Mismo patrón que `trainerName`: un `git grep` de la semilla y los specs en el mismo ticket.                                                                |
| El rename `clients` → `students` rompe enlaces                     | Un solo ticket, con `git mv`, y verificación de que ninguna ruta antigua quede referenciada.                                                               |
| El constructor de rutinas es la pantalla más compleja del proyecto | Se parte en tres tickets: cabecera, días, ejercicios por día. Cada uno navegable por separado.                                                             |
| `@capacitor/share` nunca se ha ejercitado                          | En web la API de compartir puede no existir: el botón cae a copiar el enlace, con su test.                                                                 |
| Capturar carga real puede volver pesado el runner                  | Los campos llegan precargados con lo prescrito; confirmar sin tocarlos cuesta un toque, igual que hoy. Se valida en el navegador antes de cerrar T-9.12.4. |
| `actionRoute` está en la semilla de notificaciones y en su spec    | Mismo patrón que `trainerName`: `git grep` de la semilla y los specs dentro del mismo ticket.                                                              |

## Verificación

**Por ticket**, antes de entregar el mensaje de commit:

```bash
npm run lint && npm run typecheck && npm run format:check && npm run test:coverage && npm run build
```

Las cuatro métricas ≥80% y sin warnings nuevos de budget.

**Por historia**, en navegador a **375×812 y 320×568**, con los cuatro estados de cada
pantalla y el recorrido completo con teclado.

**Al cerrar la épica**, sobre las pantallas nuevas del entrenador:

1. La skill `auditoria-component`, igual que se hizo con el alumno.
2. El barrido por script de contraste, nombres accesibles y área táctil: cero fallos.
3. Recorrido end-to-end: registrar alumno → compartir invitación → aceptarla en otra
   sesión → construir rutina → asignarla → verla desde la app del alumno.

Ese último punto es la prueba real de que los dos roles comparten los mismos puertos.
